## 1. 项目背景与目标

### 1.1 客户画像（2026-07 调研结论）

- **客户**：Southern Star Foods，高置信度为 Southern Star Distributors I, Ltd. 的商号（DBA），Plano, TX。⚠️ 待与客户当面确认实体身份。
- **实质业务**：小型 broadline 食品批发分销商，约 45 人、估算年营收 ~$28M，成立于 ~1987 年。
- **运营硬数据**（FMCSA USDOT 498144）：自营仓库 + 自有车队 21 辆卡车 / 26 名司机，跨州配送，货类含干货、生鲜、肉类、冷藏食品、饮料、纸制品。
- **现状痛点**：现用 ERP 已 20+ 年，功能落后、卡顿报错。仓库是公司命脉，故对 WMS 格外看重。

### 1.2 Demo 目标（依会议纪要重定）

1. **赢得合作**：用可运行的 demo 证明我们理解食品分销业务，能力远超其旧系统。
2. **主线故事 = 核心仓库端到端流程**：
   `发货触发/低库存 → 生成采购单 → 采购 → 核对采购货物 → 货物入库(按 SKU 定库位) → 接收订单 → 生成取货单 → 取货(告知库位) → 称重定价(catch-weight) → 发货 → 退货退款`
3. **演示核心 = catch-weight 称重定价**：客户按箱/袋下单（不按重量买），取货员取货后称重，系统按实重自动算价并生成出货单。这是食品分销 ERP 区别于普通 ERP 的最大特征，也是本 demo 最有说服力的一环。
4. **不追求完备**：明确「不做清单」（见 §3.4），管理客户预期。

### 1.3 成功标准

- 演示会上流畅走完一条完整业务故事线（见 §7），无报错。
- 客户直观感受到与旧系统的代差：catch-weight 自动定价、批次追溯秒级响应、实时告警看板。
- 演示后客户愿意进入正式合同谈判（Discovery 阶段收费立项）。

## 2. 现状盘点（2026-07-28 更新）

### 2.1 代码基础

`warehouse-demo-system`：Next.js 15（App Router）+ React 19 + TS + Tailwind 4 + Supabase（Postgres/Auth/RLS）。约 40 迁移、大量 Server Actions、中英西三语。文档体系完整（`docs/00-invariants.md` 14 条业务铁律 + ADR）。**结论：不重构，增量开发。**

⚠️ **新增项目约定（同事已加 `CLAUDE.md`）**：页面禁止硬编码中文，一律走 i18n，文案键统一放 `pg.<模块>.*` 命名空间；服务端用 `getDictionary()/t()`，客户端用 `useI18n()`。新增词条三语齐补。**本人早期写的路线页/趟次页为硬编码中文，需按此约定整改（见 Phase E）。**

### 2.2 会议纪要核心流程 → 系统覆盖情况

| 流程环节 | 系统现状 | 缺口 |
|---|---|---|

## 6. 技术方案要点

- 沿用现有架构，零新框架：Next.js Server Actions 即后端，业务护栏下沉 Postgres 触发器/RLS，领域纯函数进 `lib/domain/` 配 vitest。
- 新表一律带 RLS（`user_has_permission` 细粒度范式）+ 审计（`fn_audit_row`）。
- 全站 i18n（`messages/{zh,en,es-MX}.json`），页面文案 `pg.*` 命名空间。
- 演示数据用迁移/脚本构造，注意发运链路快照触发器；云端 dev 库改动前先备份。

## 7. 演示策略：一条订单的一生（catch-weight 为核心）

演示会故事线（约 20 分钟）：

1. **采购/入库**：某商品低库存告警 → 生成采购单 → 收货三单核对 → 按 SKU 入库上架
2. **销售**（同事）：餐厅客户下单 2 箱鸡肉（catch-weight）+ 若干干货 → 信用闸校验 → 确认订单
3. **仓库取货 + 称重**（本人，**情绪高点**）：生成取货单（告知库位）→ 取货员取 2 箱鸡肉 → **称重录入 → 系统按实重自动算价 → 生成出货单**（对比：客户按箱买，系统按磅计价）
4. **发货 + 追溯**：发运签收 → 任选批次演示「秒级双向追溯」
5. **退货退款**：一箱质量问题退货 → 隔离 → 退款/预存冲抵
6. 收尾：路线配送、移动端作为「路线图」带过 → 引出 Discovery 提案
